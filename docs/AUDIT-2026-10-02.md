# X1 Privacy — Security review, 2 October 2026

**Kind of review:** internal, AI-assisted, performed by the team that maintains
the code. It is **not** an independent third-party audit and should not be read
as one. Independent audits will be published separately.

**Verdict:** no open issue was found that lets a third party take funds from a
reserve or from a user. The open items are operational (who can upgrade the
program, how the website is hosted) and inherent privacy limits. They are listed
below without softening.

## Scope

| Component | What was reviewed |
|---|---|
| On-chain program `x1_confidential` | Full source read; unit tests; rejection simulations against the live mainnet program; on-chain state |
| Proof module `proofgen` | Key derivation, randomness, every exported function; unit tests incl. proof verification |
| Web client `ui/` | Transaction construction, key handling, DOM output, content-security policy, dependency advisories; headless-browser end-to-end tests on testnet and mainnet |
| Deployment | Deployed bytes vs. source; authorities; mint, config and reserve accounts |

Not covered: the chain's Token-2022 and ZK ElGamal proof programs (trusted
dependencies), wallet extensions, RPC infrastructure, and formal verification of
the cryptography (the module uses `solana-zk-sdk` 5.0.1 as is).

## What was verified

**Deployment (mainnet).**
- The deployed program is byte-identical to a build of this repository
  (414,992 bytes, sha256 `07288630…700be`).
- Both confidential mints: mint authority and confidential-transfer authority are
  the program-derived config account; no freeze authority; no auditor key;
  automatic account approval; same decimals as the backing token.
- Both reserves: token account of the backing mint, under the backing mint's own
  token program, owned by the config account, no delegate, no close authority.
- For both tokens, reserve balance = recorded supply = mint supply.
- Backing tokens: wrapped native XNT (no extensions); USDC.x (Token-2022 with
  metadata only — no transfer fee, hook, permanent delegate or freeze authority).
- No swap accounts exist; the program owns only config and vault accounts.

**Program logic.**
- Token programs are never taken from the caller: the confidential token program
  must own the confidential mint, the backing token program must own the backing
  mint, and every token account is checked against them.
- Wrap: the reserve must receive exactly the deposited amount; the mint's supply
  must rise by exactly the net amount; the fee can only go to the fixed
  recipient's associated token account.
- Unwrap: the burn is verified against the mint's supply before backing is
  released; exactly the burned amount leaves the reserve; the destination must be
  a token account owned by the signer and cannot be the reserve; no fee account
  is involved.
- After every wrap and unwrap the reserve must still cover the recorded supply.
- Registering a token requires the program's upgrade authority and enforces the
  mint and reserve properties above.
- The experimental swap instructions are disabled in this build
  (`open_swap` always fails), and the relay they use only accepts a
  context-state confidential transfer between validated accounts.

**Simulated attacks against the live mainnet program (nothing sent).**
Substituting another program for the token program on unwrap, paying an unwrap
out to the reserve, lowering the cap below supply or to zero, and opening a
swap are all rejected with the intended errors.

**Proof module.** Transfer and balance ciphertexts use fresh randomness (tests
assert that two proofs for the same amount differ and still verify). Predicted
ciphertexts used for chained operations are tested against the chain's
arithmetic. No key material is logged or sent anywhere.

**Web client.** No inline script; strict content-security policy; no
third-party resources; all text reaching the DOM from the network is escaped;
the token list is validated. End-to-end tests (create account, wrap, send, receive,
unwrap; both tokens; new and existing wallets; wallets with and without batch
signing) pass on testnet and on mainnet with no console errors.

**Amount limits (tested on testnet with amounts above 2^48 base units).**
- One wrap or one confidential transfer carries at most 2^48 − 1 base units
  (281,474.97 XNT; 281,474,976.71 USDC.x). This is a property of the token
  program's encoding. The client now refuses larger amounts with a clear message;
  nothing is at risk — an oversized attempt simply fails.
- Balances are 64-bit: an account can hold more than that through several wraps.
- Unwrap has no per-operation limit: an unwrap of 500,000,000 test USDC.x
  (above 2^48 base units) succeeded in one operation.

## Fixed during this review

| Item | Fix |
|---|---|
| Oversized wrap / transfer failed with an opaque proof error | Explicit per-operation limit check and message |
| A stale decryptable-balance copy made a large balance unreadable (the fallback search only reached 2^40 base units) | New `elgamal_decrypt_near`: searches the difference from the stale copy, so it works for balances of any size |
| Applying incoming funds could be split into its own transaction ahead of the spend that assumed it | It is now always in the same transaction as that spend (or the action stops and asks the user to receive first) |
| Internal names and key-file conventions in comments and defaults | Removed |

Earlier fixes (before mainnet launch) included: pinning token programs and
verifying burns and mints; restricting the swap relay; removing the fee account
from the exit path; fresh randomness in transfer proofs and balance encryption;
no persistent storage of key-derivation signatures; no server-side keys.

## Open findings

### High — operational

**O-1. Single upgrade key.** The program is upgradeable by one key, which is
also the cap governance of both tokens and the record program's upgrade
authority. Whoever controls it can replace the program. *Recommendation:* move
the upgrade authority to a multisig held on separate devices, keep an offline
backup, and define an upgrade policy (notice period, published diffs). Until
then this is the largest single risk to user funds.

**O-2. The website is a trust root.** Users sign transactions the site builds.
Anyone who can publish to the site's hosting account can serve a malicious page.
*Recommendation:* protect the hosting account with hardware-backed 2FA, use
short-lived deploy credentials that are never shared or stored in files, rotate
any credential that has been exposed, and publish the bundle hash with each
release so users and wallets can compare.

### Medium

**M-1. No independent audit, and tests need a live cluster.** Unit tests cover
pure logic; the full flows are tested end to end against testnet and mainnet but
not in a local, repeatable CI run. *Recommendation:* independent audit; a
local-validator integration suite.

**M-2. Key-derivation signature can be requested by any site.** The encryption
keys are derived from a wallet signature over a fixed binary message. A
malicious site that persuades a user to sign the same message can decrypt that
user's balances and transfer amounts (it cannot move funds). This is inherent
to the standard derivation; wallets that derive the keys internally remove it.

**M-3. Governance can stop new wraps.** The cap authority can lower a token's
cap to its current supply. This cannot block transfers or unwraps.

**M-4. Trusted dependencies.** The chain's Token-2022 program (upgradeable by
the chain's maintainers) and the native proof program hold and validate all
confidential balances.

### Low / informational

- **L-1. Dependency advisories** (`bigint-buffer`, `toml`, `qs`, `uuid` via
  Solana JS libraries and Express). None is reachable with attacker-controlled
  input in the shipped client; track upstream fixes.
- **L-2. Incoming-credit counter.** An account accepts 65,536 incoming credits
  before it must apply them. Filling it costs the sender a transaction per
  credit and is cleared by one "receive".
- **L-3. Batched approvals share one blockhash.** If the user approves late, later
  steps expire and the action must be retried; no funds are at risk.
- **L-4. Key-derivation signature is kept in `sessionStorage`** for the life of
  the tab (never in persistent storage unless a wallet signs
  non-deterministically).
- **L-5. Burning confidential tokens directly with the token program** (not
  through unwrap) destroys them without releasing backing. User error only.
- **L-6. Per-wallet vault account** publicly records net wrapped amounts
  (derivable from wrap and unwrap history anyway).
- **L-7. Swap code is disabled but still present**; remove it in a later upgrade
  to shrink the attack surface.
- **L-8. Wrap-only balances** need a 1-unit self-transfer before their first
  unwrap (identity decryption handle). The client does this automatically in the
  same approval.

## Privacy model (unchanged)

Hidden: balances and confidential transfer amounts. Public: account owners,
sender and recipient of each transfer, timing, every wrap and unwrap amount,
supply and reserve. This is confidentiality of amounts, not anonymity.
